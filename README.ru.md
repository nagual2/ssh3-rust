# SSH3 over HTTP/3
[English](README.md) | **Русский** | [Deutsch](README.de.md)

SSH3 переносит семантику удалённых сессий в духе RFC 4254 на QUIC, TLS 1.3 и HTTP/3 Extended CONNECT. Цель проекта — сохранить привычные SSH-сценарии, добавив HTTP-нативную аутентификацию и транспортные возможности QUIC, такие как пересылка датаграмм.

В репозитории сейчас две реализации:

- Оригинальные Go-клиент и Go-сервер в [`cmd/ssh3`](cmd/ssh3) и [`cmd/ssh3-server`](cmd/ssh3-server)
- Развивающийся рерайт на Rust в [crates](.)

> [!WARNING]
> Не считайте ни одну из реализаций production-ready. Протокол и код активно разрабатываются, а рерайт на Rust сосредоточен в первую очередь на корректности и совместимости, а не на продуктовой полноте.

## О форке nagual2
Этот форк нацелен на то, чтобы Go-реализация стала практичным повседневным инструментом. Этот README адаптирован из README апстрим-проекта и изменён мейнтейнерами форка; изменения только форка отслеживаются в [CHANGELOG.md](CHANGELOG.md):

- **Windows-клиент — полноценный гражданин.** Начиная с v0.1.8 клиент компилируется под Windows и поддерживает интерактивные PTY-сессии: VT-ввод/вывод, кодовую страницу UTF-8, реальный размер консоли, проброс `SIGINT`/`SIGTERM` и фолбэк PTY 80x24, если размер консоли узнать не удалось.
- **Пакеты сервера: ключи по умолчанию, пароли — opt-in.** Релизный `.deb` содержит systemd-сервис (`ssh3-server.service`, UDP 443, секретный URL-путь); OIDC не настроен, а пост-установочный скрипт генерирует self-signed сертификат ed25519 с IP/DNS SAN. В amd64-сборках парольный бекенд скомпилирован и включён по умолчанию (`SSH3_ENABLE_PASSWORD_LOGIN=0` выключает); arm-сборки сервера — только ключи.
- **systemd-юнит в паритете с OpenSSH.** В юните нет sandbox-директив (`CapabilityBoundingSet`, `NoNewPrivileges`, `Protect*`): root-демон порождает каждую сессию с uid/gid аутентифицированного пользователя (как sshd), поэтому `sudo` внутри сессии возвращает полные capabilities root — tcpdump, trafshow, modprobe и sysctl работают. `KillMode=process` сохраняет живые сессии при рестарте демона, как в Debian `ssh.service`. Граница доверия — ключевая авторизация, а не песочница юнита.
- **Баннер статистики при входе.** Интерактивные сессии перед промптом шелла показывают uptime, load, память и диск (запросы `exec` не затрагиваются).
- **Локаль и шелл.** Сервер пробрасывает `LANG`/`LC_*` из своего systemd-окружения в шеллы пользователей и запускает реальный login-шелл аккаунта из `/etc/passwd` вместо захардкоженного `/bin/sh`.
- **CI.** Каждый тег `v*` собирает релизные архивы и `.deb` через goreleaser; каждый пуш в `main` — артефакты Windows-клиента.
- **Спецификация wire-протокола.** Протокол, на котором говорит форк, оформлен как документ проекта в репозитории C17-порта: [SSH3 wire protocol, rev nagual2/1](https://github.com/nagual2/ssh3-c/blob/main/docs/SPEC-wire.md) — остов draft-michel-remote-terminal-http3-00, выверенный по обеим живым реализациям (этот форк + ssh3-c).

## Скачивание и установка
Берите ассеты из [последнего релиза](https://github.com/nagual2/ssh3-go/releases/latest):

| Файл | Назначение |
| --- | --- |
| `ssh3-go_client_<ver>_windows_amd64.zip` | Клиент для Windows (`ssh3.exe`) |
| `ssh3-go_client_<ver>_<os>_<arch>.tar.gz` | Клиент для Linux, macOS, FreeBSD, OpenBSD |
| `ssh3-go_server_<ver>_linux_<arch>.tar.gz` | Серверные бинарники для Linux |
| `ssh3-go_<ver>_amd64.deb` | Пакет сервер + клиент для Debian/Ubuntu/Mint (systemd-сервис, пароли включены по умолчанию на amd64 (`SSH3_ENABLE_PASSWORD_LOGIN=0` выключает)) |

Установка deb-пакета:

```bash
sudo dpkg -i ssh3-go_0.1.26_amd64.deb
```

Пакет `ssh3-go` заменяет прежний пакет `ssh3` на месте (Conflicts/Replaces); бинарники (`ssh3`, `ssh3-server`) и юнит `ssh3-server.service` сохраняют имена.

Сервис слушает UDP 443 по секретному URL-пути `/ssh3-term`. Конфигурация — в `/etc/ssh3/ssh3-server.env` (файл и уровень лога, `LANG`), юнит — в `/usr/lib/systemd/system/ssh3-server.service`, а self-signed сертификат ed25519 с IP/DNS SAN генерируется в `/etc/ssh3/` при установке, если его нет.

### Конфигурация сервера
Релизный пакет настраивается через systemd `EnvironmentFile` — `/etc/ssh3/ssh3-server.env`:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SSH3_LOG_FILE` | `/var/log/ssh3.log` | Файл журнала сервера |
| `SSH3_LOG_LEVEL` | `info` | Уровень логирования (`trace`, `debug`, `info`, `warn`, `error`) |
| `SSH3_GATEWAY_PORTS` | `no` | Политика GatewayPorts для обратного (-R) форвардинга: `no` принудительно возвращает запрошенные не-loopback бинды на loopback, `clientspecified` чтит запрошенный адрес, `yes` биндит wildcard |
| `SSH3_MAX_REVERSE_FORWARDS` | `10` | Максимум активных -R-слушателей на пользователя |
| `SSH3_MAX_UNAUTH_CONVERSATIONS` | `100` | Максимум конверсаций в неаутентифицированной фазе до отказов (DoS-защита) |
| `SSH3_MAX_PASSWORD_FAILURES` | `10` | Неудачных парольных попыток до блокировки аккаунта |
| `SSH3_PASSWORD_LOCKOUT_SECONDS` | `60` | Длительность блокировки от брутфорса пароля, секунды |
| `LANG` | `C.UTF-8` | Локаль, пробрасываемая в шеллы пользователей |

Применение изменений: `sudo systemctl restart ssh3-server`.

Клиент и сервер принимают флаги тюнинга QUIC-транспорта для bulk-передач: `-initial-packet-size` (размер стартового QUIC-пакета в байтах, по умолчанию `1350`), `-stream-rx-mb` (окно flow control на поток в МиБ, по умолчанию `8`), `-conn-rx-mb` (соединительное окно в МиБ, по умолчанию `16`).

## Интерактивные escape-последовательности
Escape-символ в начале строки управляет клиентом: `~.` разрывает соединение, `~^Z` подвешивает клиент локально (unix), `~~` шлёт один литеральный `~`; неизвестная последовательность уходит как есть. Символ по умолчанию `~`, выбирается через `-o EscapeChar=<символ|none>` или тот же ключ в `~/.ssh/config`.

## Заметки о Windows-клиенте
- Флаги (например, `-privkey`) должны стоять **до** позиционного URL: парсер флагов Go останавливается на первом позиционном аргументе.
- Консоль на время сессии переключается в UTF-8 и VT-режим, при выходе настройки восстанавливаются. Используйте шрифт с поддержкой Unicode (Consolas, Lucida Console).
- На Windows нет `/dev/tty`, поэтому интерактивный TOFU-промпт не работает: закрепите сертификат сервера в `%USERPROFILE%\.ssh3\known_hosts` (`host:port/path x509-certificate <base64 DER>`) или осознанно используйте `-insecure`.
- Проброс SSH-агента недоступен (только unix-сокет); изменение размера окна не пробрасывается (нет аналога SIGWINCH).

## Статус
Go-реализация по-прежнему обладает самым широким CLI-поверхностью. Rust-воркспейс покрывает ядро протокола, bootstrap QUIC/HTTP/3, аутентификацию, работу с сессиями, PTY-шеллы, проброс изменений размера и сигналов, рантаймы форвардинга и реальные тесты совместимости Rust<->Go.

Rust уже не просто эксперимент с кодеками: там есть рабочие клиент и сервер, но часть эксплуатационных функций пока есть только в Go.

## Сборка
### Rust
Нужен недавний стабильный Rust.

```bash
cargo build --workspace
cargo run -p ssh3-client -- --help
cargo run -p ssh3-server -- --help
```

Текущий CLI Rust:

```text
$ cargo run -p ssh3-client -- --help
Usage: ssh3-client [OPTIONS] <URL> [COMMAND]...

$ cargo run -p ssh3-server -- --help
Usage: ssh3-server [OPTIONS]
```

Для Rust-клиента предпочтительны файловые секреты (`--password-file`, `--bearer-token-file`, `--oidc-client-secret-file`) вместо передачи секретов прямо в командной строке: они меньше рискуют утечь через историю шелла, список процессов и логи CI.

### Go
Нужен Go 1.21+. В репозитории лежит полное дерево `vendor/`, поэтому
сборки ниже работают как есть:

```bash
CGO_ENABLED=0 go build -o ssh3 ./cmd/ssh3
CGO_ENABLED=0 go build -tags disable_password_auth -o ssh3-server ./cmd/ssh3-server
```

Релизные сборки клиента и arm-сборки сервера используют `CGO_ENABLED=0` с `-tags disable_password_auth` — парольная аутентификация полностью выпилена из бинарника. Релизный amd64-сервер собирается с CGO и без тега: shadow/crypt-бекенд скомпилирован и включён по умолчанию (`SSH3_ENABLE_PASSWORD_LOGIN=0` выключает). Релизные клиентские сборки не могут аутентифицироваться паролем. Если нужен парольный клиент в собственной Linux-сборке:

```bash
CGO_ENABLED=1 go build -o ssh3-server ./cmd/ssh3-server
```

## Быстрый старт
### Локальные Rust-сервер + Rust-клиент
Rust-сервер стартует с self-signed сертификатом, поэтому в примерах клиента используется `--insecure`.

Запуск сервера:

```bash
cargo run -p ssh3-server -- \
  --bind 127.0.0.1:4433 \
  --user "$USER" \
  --require-auth \
  --authorized-identity ~/.ssh/authorized_keys
```

Подключение приватным ключом:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --identity ~/.ssh/id_ed25519 \
  https://127.0.0.1:4433/ssh3-term
```

Удалённая команда вместо шелла:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --identity ~/.ssh/id_ed25519 \
  https://127.0.0.1:4433/ssh3-term \
  -- "printf 'hello from ssh3\n'"
```

### Go-сервер для публичных сценариев
Если нужны автоматизация публичных сертификатов, секретный URL-путь, proxy jump или CLI-форвардинг — используйте Go-бинарники.

Пример Go-сервера с публичным сертификатом:

```bash
ssh3-server -generate-public-cert my-domain.example.org -url-path /ssh3
```

Пример Go-клиента:

```bash
ssh3 -i ~/.ssh/id_ed25519 username@my-domain.example.org/ssh3
```

Для релизного сервера:

```bash
ssh3 max@my-server.example.org/ssh3-term -i ~/.ssh/id_ed25519
```

### Передача файлов

Stage 2 добавляет режим `ssh3 -transfer` поверх отдельного SFTP-канала (созданные
файлы принадлежат сессионному пользователю). Изоляция путей по умолчанию
следует модели sshd (`-sftp-jail chroot`): сервер перезапускает короткоживущий
дочерний процесс на сессию, который делает chroot в домашний каталог
пользователя и сбрасывает uid/gid до первого обращения к пути — изоляцию
обеспечивает ядро, а сетевой процесс никогда не открывает файлы пользователя.
`-sftp-jail lexical` сохраняет исторический in-process джейл (лексическая
проверка префикса; действуют привилегии самого процесса сервера — имеет
смысл только для непривилегированного однопользовательского сервера):

```bash
# загрузка файла (remote-операнд последний)
ssh3 -transfer ~/report.pdf max@my-server.example.org/ssh3-term:docs/report.pdf

# загрузка каталога целиком, рекурсивно
ssh3 -transfer -r ~/project-dir max@my-server.example.org/ssh3-term:backups/

# скачивание (remote-операнд первый)
ssh3 -transfer max@my-server.example.org/ssh3-term:logs/app.log ./app.log

# докачка прерванных передач вместо перезаписи
ssh3 -transfer --continue big-disk-image.raw max@my-server.example.org/ssh3-term:images/raw

# форсировать проверку SHA-256 перечитыванием удалённого файла
# (автоматически для передач больше 32 МиБ)
ssh3 -transfer --checksum data.bin max@my-server.example.org/ssh3-term:data.bin
```

Примечания: порт по умолчанию 443, URL-путь — `/ssh3-term`; переопределяются
флагами `-p` (ssh2-форма) и `-U`, либо полной формой операнда
`user@host:port/url_path:remote_path` (форковский `-P` в режиме передачи
работает как устаревший алиас `-p`). Нерегулярные файлы (симлинки,
устройства) пропускаются при рекурсивной передаче, пустой каталог создаётся
на противоположной стороне. Старая форковская форма передачи `-f` выведена —
флаг теперь означает ssh2-фоновый режим (таблица паритета выше).

## Контроль-мастер (мультиплексирование соединений)

Одно аутентифицированное соединение на множество вызовов - первый запуск
делает хендшейк, остальные пользуются им через Unix-сокет (stage 3.5):

```bash
# запустить постоянный мастер в фоне (команда возвращается сразу)
ssh3 -M -o ControlPersist=yes user@host

# последующие вызовы работают как slave: без нового хендшейка, старт ~5x быстрее
ssh3 -control-master=auto user@host 'uptime'
ssh3 -control-master=auto user@host 'tail -n 5 /var/log/syslog'
ssh3 -control-master=auto -L 8080:127.0.0.1:80 user@host 'sleep 30'

# остановить мастер
ssh3 -O exit -S ~/.ssh3/cm-user@host:443 user@host
```

| Флаг | Значение |
|------|----------|
| `-M` | режим мастера (ssh2 `-M`), то же, что `-control-master yes` |
| `-S PATH` | путь к управляющему сокету (ssh2 `-S`), то же, что `-control-path PATH` |
| `-control-master no\|yes\|auto` | `auto` использует работающий мастер и запускает новый, если его нет; `yes` всегда запускает; по умолчанию `no` (также `-o ControlMaster=…`) |
| `-control-path PATH` | путь к управляющему сокету; по умолчанию `~/.ssh3/cm-<user>@<host>:<port>`, права 0600 (также `-o ControlPath=…`) |
| `-control-persist no\|yes\|<секунды>` | держать мастера в фоне после конца сессий; `yes` = вечно, число = таймаут простоя (также `-o ControlPersist=…`) |
| `-O check\|stop\|exit` | управляющая операция на работающем мастере; операнд-цель всё ещё нужен, если не задан явный `-control-path`, а неизвестное значение отвергается заранее со списком поддерживаемых |

Примечания: мастер - отсоединённая копия этого же бинарника
(`SSH3_CM_DAEMON=1`); каждая slave-сессия, TCP/UDP-форвард и agent
forwarding мультиплексируются через единственное QUIC-соединение мастера.
Медиана 100 последовательных exec падает с ~130 мс (холодный путь, хендшейк
на каждый) до ~24 мс (~17%) при ровно одном хендшейке. Ограничения:
`-J`/`-proxy-jump` несовместим (сочетание с `-control-master` — ошибка), Windows
не поддерживается. Интерактивные pty-slave-сессии пробрасывают через мастер
изменение размера терминала и внеполосные сигналы. Управляющий сокет,
оставшийся от убитого мастера, обнаруживается и удаляется, а не приводит к
`EADDRINUSE` на всё время ожидания, поэтому «протухший» путь больше не
блокирует следующий запуск.

### Управляющие операции

| Операция | Поведение |
|----------|-----------|
| `-O check` | напечатать состояние мастера (pid, время работы, активные сессии, проброшенные каналы) в stdout и выйти с кодом 0 |
| `-O stop` | остановить мастера и дождаться, пока управляющий сокет действительно будет освобождён |
| `-O exit` | остановить мастера (историческое поведение) |

`check` стоит один управляющий round trip и не открывает сессию, поэтому
достаточно дёшев для опроса из скриптов и оркестраторов. Если мастер не
слушает, команда завершается внятной ошибкой с ненулевым кодом возврата, а
не висит. Операция, которой сборка не знает, отклоняется мастером с
понятной ошибкой, а соединение остаётся пригодным для корректного повтора.

Все три операции доступны из командной строки: `check`, `stop` и `exit`
разбираются и на быстром пути с `-control-path`, и на обычном, а значение вне
этого набора отвергается заранее, со списком поддерживаемых — ещё до чтения
ключей и known_hosts:

```bash
# спросить у работающего мастера его состояние
ssh3 -O check user@host

# остановить и дождаться реального освобождения управляющего сокета
ssh3 -O stop user@host
```

`exit` намеренно остаётся на историческом управляющем кадре, чтобы мастера
версий v0.1.22/v0.1.23 по-прежнему корректно выключались. Новые операции к
более старому мастеру дают явную ошибку «the control master does not support
… control operation», то есть старый пиер отклоняет их сразу, а не оставляет
клиент ждать.

## Проброс портов
Локальные форварды туннелируются через ssh3-соединение. Основная форма —
ssh2-синтаксис `-L [bind:]port:host:hostport`, повторяемый; необязательный
префикс `udp://` выбирает UDP, которого в ssh(1) нет:

```bash
# ssh2-форма: локальный 8080 к дозвону сервера на 10.0.0.10:80
ssh3 -L 8080:10.0.0.10:80 user@host

# явный локальный адрес; IPv6-литералы в скобках
ssh3 -L 127.0.0.1:8080:10.0.0.10:80 user@host
ssh3 -L '[::1]:8080:[::1]:80' user@host

# UDP — документированное расширение ssh3 (префикс udp://)
ssh3 -L udp://5353:192.0.2.1:53 user@host
```

Форковская форма `локальный_порт/удалённый_ip@удалённый_порт` работает как
устаревший алиас:

```bash
ssh3 -forward-tcp 8080/10.0.0.10@80 user@host
ssh3 -forward-udp 5353/192.0.2.1@53 user@host
```

`-N` держит соединение открытым для форвардов без запуска сессии;
`Ctrl+C` закрывает его:

```bash
ssh3 -N -L 8080:10.0.0.10:80 user@host
```

### Обратный проброс (`-R`)

`-R` просит **сервер** забиндить слушатель и мостить каждое принятое им
соединение обратно к цели на стороне клиента.

```bash
# сервер слушает 127.0.0.1:8080 и мостит его на локальный 127.0.0.1:80
ssh3 -N -R 8080:127.0.0.1:80 user@host

# UDP-пир на сервере достаёт до локального резолвера
ssh3 -N -R 5353/udp:127.0.0.1:53 user@host

# привязка на всех интерфейсах (сервер пишет предупреждение о широкой привязке)
ssh3 -N -R '*:8080:127.0.0.1:80' user@host
```

Флаг задаётся как `[bind_address:]bind_port[/udp]:target_host:target_port` и
может повторяться. По умолчанию TCP, суффикс `/udp` после порта привязки
выбирает UDP. Без адреса привязки — и с `localhost`, `127.0.0.1` или `::1` —
сервер слушает только свой loopback; `*` (как и `0.0.0.0` и `::`) требует
wildcard-привязки, которую сервер разрешает, но логирует с предупреждением.
**Цель резолвится на клиенте**, как в OpenSSH, поэтому сервер получает только
IP-литерал. Обычный спутник `-N`: без сессии цикл разбора сервер-инициируемых
каналов никто не запустил бы.

Семантика: каждый клиентский управляющий канал `reverse-forward` несёт один
запрос привязки как данные канала, а сервер отвечает занятым портом — порт
привязки `0` просит эфемерный, и фактический порт попадает в лог. Каждое
принятое соединение затем зеркалится обратно как **сервер-инициируемый канал
`forwarded-tcp`**, чьи дополнительные байты заголовка несут клиентскую цель
(для UDP — по одному каналу `forwarded-udp` на каждого удалённого пира, как и
в прямом UDP-форвардинге). Клиент мостит только тот канал, цель которого
действительно запрошена через `-R`, поэтому скомпрометированный сервер не
заставит клиент дозвониться до произвольной локальной точки, а одновременно
открыто не более 64 каналов на беседу. Закрытие управляющего канала или
соединения освобождает привязку.

`-R` отвергается на уровне командной строки вместе с `-control-master` и
`-f`. Старый сервер, не знающий этого канала, закрывает его без ответа, и
клиент сообщает об этом как «the server does not support reverse forwarding»,
а не виснет; нужен сервер версии v0.1.23 или новее.

### Динамический SOCKS-проброс (`-D`)

`-D [bind_address:]port` открывает локальный SOCKS5-прокси, соединения
которого дозванивает удалённый пир, — аналог `-D` из OpenSSH:

```bash
# SOCKS5-прокси на 127.0.0.1:1080, интерактивная сессия не страдает
ssh3 -D 1080 user@host

# слушать на всех интерфейсах и держать соединение только ради прокси
ssh3 -N -D '*:1080' user@host

# порт выбирает ядро; выбранный попадает в лог
ssh3 -D 0 user@host
```

Прокси говорит только по методу SOCKS5 *no authentication required* (он
биндит локальный слушатель и пробрасывает соединение внутри ssh3, поэтому
никогда не видит учётных данных), поддерживает команду `CONNECT` и принимает
типы адресов IPv4, IPv6 и домен. Без адреса привязки слушатель вешается на
loopback, `*` — на все интерфейсы; IPv6-литерал должен быть в квадратных
скобках, поэтому голое `::1:1080` отвергается, а не читается неверно. Как и
прямые форварды, динамический можно сочетать с сессией или с `-N`; в случае
`-N` цикл разбора каналов запускает сам клиент.

Протокол использует два типа каналов:

1. Клиент открывает один управляющий канал `dynamic-forward` и отправляет
   в него сообщение о привязке как данные канала. Сервер ничего не
   привязывает — он лишь подтверждает, что будет обслуживать SOCKS-слушатель
   клиента.
2. Для каждого принятого слушателем соединения клиент открывает канал
   `dynamic-forward-tcp` с адресом цели. Сервер сам резолвит этот адрес,
   сам поднимает TCP-соединение и связывает канал с этим соединением.
   **Доменное имя передаётся как есть** и резолвится сервером, потому что
   SOCKS-клиент часто знает только имя.

Новых message-type ID не вводилось: `ParseMessage` паникует на неизвестных
ID, из-за чего старые пиеры падали бы вместо graceful-отказа. Поэтому все
полезные нагрузки идут обычными данными канала за версионированным префиксом
(версия протокола 1 + вид сообщения), и старый пиер их просто не видит.

По каждому соединению сервер отвечает результатом дозвона, поэтому ошибка
резолвинга или подключения доходит до SOCKS-клиента читаемой причиной, а не
молчаливым зависанием; текстовая причина отображается в соответствующий код
ответа SOCKS5 (`connection refused`, `host unreachable`, `ttl expired`, …),
так что клиент не видит безликого «general failure». Одновременно в одной
беседе bridging ограничен 64 каналами `dynamic-forward-tcp`, а закрытие
управляющего канала или самой беседы срывает все живые bridging-соединения.
Обе половины лежат в невыпущенном дереве, поэтому `-D` требует сервера,
собранного из этого источника.

## Совместимость с OpenSSH (ssh2-канон)

Где функционал совпадает, ключи запуска следуют ssh(1)/sshd(8) — скрипты,
написанные под OpenSSH и под сестринскую C-реализацию, ведут себя одинаково
с этим клиентом (волна CLI-паритета, CTO_TASK §7c). Форковские формы
сохранены как устаревшие алиасы: живые установки и существующие скрипты
продолжают работать.

| ssh2-форма | Смысл | Устаревший форковский алиас |
|---|---|---|
| `-i ФАЙЛ` | приватный ключ для pubkey-аутентификации | `-privkey ФАЙЛ` |
| `-V` | напечатать версию и выйти | `-version` |
| `-A` | проброс SSH-агента | `-forward-agent` |
| `-J ЦЕЛЬ[,ЦЕЛЬ...]` | proxy jump; каждый хоп должен работать под ssh3-server | `-proxy-jump URL` (один хоп) |
| `-L [BIND:]PORT:HOST:PORT` | локальный форвард, повторяемый; префикс `udp://` выбирает UDP | `-forward-tcp/-forward-udp ЛОКАЛЬНЫЙ/УДАЛЁННЫЙ@ПОРТ` |
| `-M` / `-S ПУТЬ` | режим мастера / управляющий сокет | `-control-master yes` / `-control-path ПУТЬ` |
| `-p ПОРТ` | удалённый порт (также в режиме передачи) | `-P ПОРТ` (только режим передачи) |
| `-q` | тихий режим: без диагностики, ошибки остаются | — |
| `-4` / `-6` | принудительное семейство адресов | — |
| `-f` | уйти в фон после старта (ssh2 `-f`): сессия отвязывается от терминала и продолжает работать; только неинтерактивная аутентификация (ключ/агент), незакреплённый хост при политике ask по умолчанию отвергается заранее; сочетается с командой, `-N` или форвардами (`-L/-D/-R`); на Windows недоступно (работает в foreground с предупреждением) | — |
| `-transfer SRC DST` | режим передачи файлов | форковская форма передачи `-f` выведена (флаг теперь означает ssh2-фон) |

Сервер (канон sshd(8)): `-h КЛЮЧ` = host key (алиас `-key`), `-c СЕРТ` =
host-сертификат (алиас `-cert`), `-p ПОРТ` = порт слушателя (переопределяет
порт `-bind`, сам адрес остаётся в `-bind` — QUIC нужен явный UDP-адрес),
`-V` = версия.

Ключи `-o` по модели ssh_config: `Port`, `User`, `IdentityFile`,
`LocalForward`, `RemoteForward`, `DynamicForward`, `ProxyJump`,
`ControlMaster`, `ControlPath`, `ControlPersist` (рядом с существующими
`StrictHostKeyChecking`, `EscapeChar`, `RequestTTY`, `Term`,
`VerifyHostKeyDNS`). Приоритет: флаг CLI > `-o` > `~/.ssh/config`.

Поведенческие таймауты следуют канону sshd: простаивающая сессия не убивается
(форма `ClientAliveInterval=0` — дефолтный idle-таймаут 24 ч на обеих
сторонах, настраивается `-max-idle-timeout`), хендшейку отведён масштаб
`LoginGraceTime` (120 с, `-handshake-idle-timeout`). Учётная запись root
всегда отвергает парольную аутентификацию (аналог
`PermitRootLogin prohibit-password`): root входит только по ключу.

## Знакомые флаги ssh(1)
### Принудительный PTY (`-t`)

Если на локальной стороне нет терминала — пайп, cron-задача, отсоединённый
запуск — PTY не запрашивается, и удалённые полноэкранные программы
отказываются стартовать. `-t` запрашивает его принудительно:

```bash
# запустить полноэкранную программу с pty, даже когда stdin — пайп
ssh3 -t user@host 'htop'

# интерактивный шелл с pty, геометрия берётся из локальной консоли
ssh3 -t user@host
```

Тип терминала берётся из `$TERM` (`xterm`, если переменная не задана),
геометрия — из локальной консоли, с фолбэком **80x24**, когда её узнать не
удалось: PTY с геометрией по умолчанию всё равно лучше голого пайпа.
`SIGHUP`, `SIGINT`, `SIGQUIT` и `SIGTERM` пробрасываются в удалённый PTY, а на
unix `SIGWINCH` превращается в запрос смены размера окна, так что
`ssh3 -t user@host top` остаётся изменяемым по размеру. На Windows
`SIGWINCH` нет: консоль сообщает о resize событием, а не сигналом, поэтому
геометрия, отправленная вместе с запросом PTY, действует на всю сессию.

### Запросы подсистем (`-s`)

`-s NAME` запрашивает удалённую подсистему вместо шелла или команды:

```bash
# интерактивный sftp-шелл по выделенному каналу sftp
ssh3 -s sftp user@host
```

`sftp` отдельно обрабатывается интерактивным SFTP-клиентом, команды которого —
`pwd`, `ls`, `cd`, `get`, `put`, `mkdir`, `rm`, `rmdir`, `help`,
`quit`/`exit`, то есть полезная часть `sftp(1)` для сессии за промптом. Любое
другое имя отправляется как запрос подсистемы в канале сессии, ровно как в
`ssh(1)`; штатный Go-сервер отвечает на такой запрос «not implemented», так
что произвольное имя имеет смысл только против сервера, который подсистемы
обслуживает. С `-t` PTY запрашивается до подсистемы.

`-s` владеет каналом сессии, поэтому отвергается на уровне командной строки
вместе с `-f`, `-N`, `-forward-agent`, `-R` и удалённой командой.

### Альтернативный файл конфигурации (`-F`)

`-F PATH` читает пользовательский файл конфигурации, отличный от
`~/.ssh/config`; без `-F` клиент читает `~/.ssh/config` как обычно. Путь
используется дословно, как в OpenSSH, поэтому относительный путь остаётся
относительно текущего каталога:

```bash
ssh3 -F ./ci/ssh_config user@host 'uptime'
ssh3 -F /home/deploy/.ssh/config.work user@host
```

Всё описанное в следующем разделе — `Host`, `Match`, `Include` — разрешается
из этого файла точно так же. Нечитаемый путь не роняет соединение: ошибка
чтения уходит в stderr и конфиг игнорируется, а отсутствующий файл просто
пропускается молча.

## Конфигурация клиента (~/.ssh/config)
Помимо `HostName`, `Port`, `User` и `IdentityFile` клиент учитывает по
шаблону `Host`: `ProxyJump` (интерпретируется как ssh3 UDP proxy jump:
jump-хост должен работать под ssh3-server), `UDPProxyJump` (расширение
форка, та же семантика), `ForwardAgent` и `ServerAliveInterval` (секунды;
настраивает QUIC keepalive, по умолчанию 1).

### Блоки `Match`
`Match` разрешается пре-парсером, который до запуска декодера ssh_config
разворачивает в плоский вид только те блоки, что применимы к запрошенному
алиасу, поэтому приоритеты «первое полученное значение выигрывает» из
`ssh_config(5)` сохраняются. Поддерживаемые критерии: `all`, `final`,
`host`, `originalhost`, `user`, `localuser` и `exec`, с отрицанием через
`!` и glob-шаблонами. Конфиги без блоков `Match` идут по неизменённому
быстрому пути.

```text
Host example.lan
    User deploy
    Match originalhost web*
        Port 2222
    Match exec "test -f /srv/maintenance"
        ForwardAgent no
```

Два упрощения, специфичных для ssh3, следуют из того, что конфиг
применяется за один проход, а имена хостов не канонизируются: `final`
срабатывает всегда, `canonical` — никогда. `host` и `user` вычисляются по
эволюционирующей цели, поэтому `HostName` или `User`, заданные более ранним
применимым блоком, видны и последующим блокам `Match`. `exec` выполняется
через `sh -c` на unix и `cmd /c` на Windows и считается успешным при коде
возврата 0.

### `Match` внутри файлов `Include`
`Include` разворачивает тот же пре-парсер, рекурсивно и *до* разбора всего
остального: содержимое включаемого файла занимает место самой директивы и
продолжает окружающий блок `Host` или `Match` — ровно как в OpenSSH.

```text
Include ~/.ssh/config.d/*.conf

# ~/.ssh/config.d/web.conf
Match host web*
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_web
```

Раньше любой `Match`, достигнутый через `Include`, ронял декодер
ssh_config, и весь `~/.ssh/config` отбрасывался. Теперь включённый блок
`Host` или `Match` проходит ту же фильтрацию по алиасу и `Match`, что и
основной файл. Поддерживаются glob-шаблоны в целях `Include`, вложенные
включения, защита от циклических включений и ограничение глубины рекурсии
16. Отсутствующий или нечитаемый включаемый файл пропускается, а не
аннулирует остальную конфигурацию, и ошибка разбора `Match` указывает
включаемый файл и ту самую строку, в которой она находится.

### Проверка хоста по SSHFP (RFC 4255)
Движок SSHFP сверяет DNS-записи типа 44, опубликованные для хоста, с
настоящим отпечатком предъявленного ключа хоста. Отпечаток считается по
**DER-сертификату X.509 хоста**: ssh3 пинит сертификаты, а не сырые SSH
public key. Формат DNS собирается и разбирается внутри проекта, поэтому
сторонний резолвер не нужен.

По умолчанию выключено, как в OpenSSH; включается через `-o
VerifyHostKeyDNS=...` или тем же ключом в `~/.ssh/config`, с привычным
приоритетом источников (`-o` > `~/.ssh/config`, а значение по умолчанию
остаётся выключенным):

```bash
# отвергнуть хост, если опубликованные записи SSHFP не совпали с его ключом
ssh3 -o VerifyHostKeyDNS=yes user@host

# ограничить запрос определёнными алгоритмами ключа хоста
ssh3 -o VerifyHostKeyDNS=yes:ed25519,rsa user@host

# тот же ключ по хосту в ~/.ssh/config
```

```text
Host example.lan
    VerifyHostKeyDNS yes:ed25519
```

Принимаемые значения:

| Значение | Смысл |
| --- | --- |
| `no` (также `false`, `off`, пусто) | запроса нет вовсе — значение по умолчанию, без DNS-трафика и лишней задержки |
| `ask` | проверять записи, если они опубликованы |
| `yes` (также `true`, `on`) | проверять записи и требовать совпадения |
| `yes:algo[,algo...]` | то же, но только для перечисленных алгоритмов ключа хоста |

Сравнение регистронезависимое, окружающие пробелы игнорируются. Список
алгоритмов принимает короткие и полные имена публичных ключей — `rsa`,
`ssh-rsa`, `dsa`, `ssh-dss`, `ssh-dsa`, `ecdsa`, `ecdsa-sha2-nistp256`,
`ecdsa-sha2-nistp384`, `ecdsa-sha2-nistp521`, `sk-ecdsa-sha2-nistp256`,
`ed25519`, `ssh-ed25519` — а также имена дайджестов `sha1` и `sha256`, которые
OpenSSH тоже принимает ради совместимости. Ключ хоста вне списка просто не
покрывается запросом, и для него проверка пропускается. Неизвестное значение
или неизвестный алгоритм отвергаются до установления соединения, с тем же
*«Bad configuration option»*, что и любой другой некорректный `-o`.

Политика намеренно осторожна:

- **Отклонить хоста может только несовпадение**: записи были опубликованы,
  были получены, и ни одна не совпала с предъявленным ключом. NXDOMAIN,
  пустой ответ, обрезанная датаграмма, таймаут, недоступный резолвер и
  сетевые ошибки — это *мягкий пропуск*: соединение продолжается по решению
  known_hosts. Это строго дополнительный сигнал поверх проверки known_hosts,
  а не её замена.
- `ask` не задаёт вопросов. Несовпадение при `ask` отвергает соединение с
  предупреждением, называющим опцию, которой его можно переопределить.
- С `-o StrictHostKeyChecking=no` несовпадение только предупреждает, и
  соединение продолжается — ровно так же, как проверка закреплённого
  сертификата ведёт себя при смене сертификата.
- Обмен ограничен таймаутом **2 с** по умолчанию, серверы опрашиваются
  последовательно.
- Запрос выполняется сразу после установления соединения, по тому же
  сертификату, который проверила known_hosts-проверка, и спрашивает чистое
  DNS-имя (`user@` и `:port` никакого DNS-смысла не имеют). `-insecure`
  пропускает проверку хоста целиком, а значит и SSHFP.
- В Windows конфигурация резолверов лежит в реестре, а не в
  `/etc/resolv.conf`, поэтому серверы читаются из локальных адаптеров через
  `GetAdaptersAddresses`. Если перечисление ничего не дало, запрос является
  мягким пропуском, а не ошибкой.
- Распознаются алгоритмы записей RSA, DSA, ECDSA и Ed25519; вычисляются
  отпечатки SHA-1 и SHA-256. Ключи хостов RSA, ECDSA и Ed25519 сверяются с
  ними.

Проверка живёт в невыпущенном дереве, поэтому сквозной прогон требует и
клиента, и сервера, собранных из этого источника.


## Аутентификация
### Публичный ключ
Rust-клиент:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --identity ~/.ssh/id_ed25519 \
  https://127.0.0.1:4433/ssh3-term
```

Сервер читает `~/.ssh3/authorized_identities` или стандартный `~/.ssh/authorized_keys` целевого пользователя.

### SSH-агент
Rust-клиент:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --agent \
  https://127.0.0.1:4433/ssh3-term
```

Проброс локального агента в удалённую сессию:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --agent \
  --forward-agent \
  https://127.0.0.1:4433/ssh3-term
```

### Пароль
Go-сервер (amd64-релизные пакеты содержат бекенд в бинарнике, включён по умолчанию; `SSH3_ENABLE_PASSWORD_LOGIN=0` выключает). Запуск с паролем:

```bash
ssh3-server ... -enable-password-login
```

либо для systemd-сервиса — в `/etc/ssh3/ssh3-server.env`:

```bash
SSH3_ENABLE_PASSWORD_LOGIN=1
```

с последующим `sudo systemctl restart ssh3-server`. Подключение Go-клиентом:

```bash
ssh3 -use-password username@my-server.example.org/ssh3-term
```

Go-клиент запрашивает пароль интерактивно в терминале; пароль никогда не передаётся аргументом командной строки.

Rust-вариант (сервер/клиент):

```bash
cargo run -p ssh3-server -- \
  --bind 127.0.0.1:4433 \
  --user "$USER" \
  --require-auth \
  --enable-password-login
```

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --password-file /path/to/password.txt \
  https://127.0.0.1:4433/ssh3-term
```

Примечание: arm-сборки сервера собраны с `-tags disable_password_auth` (только ключи); там парольный путь существует только в собственных сборках.

### OpenID Connect
OIDC в Rust-клиенте конфигурируется флагами, а не конфиг-файлом:

```bash
cargo run -p ssh3-client -- \
  --insecure \
  --user "$USER" \
  --use-oidc https://issuer.example \
  --oidc-client-id your-client-id \
  --oidc-client-secret-file /path/to/oidc-client-secret.txt \
  https://127.0.0.1:4433/ssh3-term
```

Авторизованные OIDC-идентичности можно перечислять в `authorized_identities` наряду с публичными ключами:

```text
oidc <client_id> <issuer_url> <email>
```

## Тестирование
Rust-воркспейс — основной путь верификации в этом репозитории.

Полный Rust-набор:

```bash
cargo test
```

Самая глубокая матрица совместимости Rust/Go:

```bash
cargo test -p ssh3-client
```

Interop-набор гоняет реальные Rust- и Go-бинарники друг против друга:

- сессии exec и shell;
- выделение PTY, resize и проброс сигналов;
- аутентификация по ключу, паролю и OIDC;
- SSH-агент и проброс агента;
- TCP- и UDP-форвардинг.

При прямом запуске Go-команд хватает vendored-зависимостей:

```bash
go build ./...
```

## Известные ограничения
- Rust-сервер сегодня намеренно минимален: только self-signed сертификаты, без секретного URL-пути и без автоматизации публичных сертификатов.
- CLI Rust пока не отдаёт флаги TCP- и UDP-форвардинга и proxy jump, хотя рантайм реализован и протестирован.
- Обратный проброс (`-R`) и динамический SOCKS-проброс (`-D`) есть только в Go-клиенте и Go-сервере, и оба появились позже последнего релиза: сервер, который их не знает, отвергает запрос явной ошибкой «not supported».
- Windows-клиент не умеет пробрасывать SSH-агент и не пробрасывает изменение размера окна (в Go там нет `SIGWINCH`); первое подключение к self-signed серверу требует закрепления сертификата в `known_hosts`, потому что интерактивному TOFU-промпту нужен tty в стиле Unix.
- Go-сервер не реализует запросы подсистем, поэтому сегодня пригодна только подсистема `sftp` (`ssh3 -s sftp`).

## Безопасность
SSH3 перспективен, но проекту нужна серьёзная проверка, прежде чем доверять ему в production. Поверхность протокола объединяет TLS 1.3, QUIC, HTTP-авторизацию и семантику каналов в стиле SSH, поэтому правильный стандарт — долгий период ревью и проверки совместимости, а не «у меня работает».

Используйте в лабораториях, CI, приватных средах и interop-экспериментах. Не полагайтесь на него как на готовую production-замену OpenSSH.
